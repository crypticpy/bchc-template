# Content model reference

`_data/schema.yml` is the single source of truth for what an entry is. Everything downstream reads it at build time or generation time — nothing about the field list is hardcoded elsewhere:

- The entry detail page and catalog cards — `_layouts/entry.html`, `_includes/entry-card.html`, `_includes/field-value.html`
- The filter panel and search index — `_includes/facet-filters.html`, `_plugins/search_index.rb` (`/search.json`)
- The public `/submit/` web form — `submit/index.md`
- The GitHub issue form — `.github/ISSUE_TEMPLATE/new-entry.yml` (generated by `npm run generate`; do not hand-edit)
- The issue → pull request scaffolder — `scripts/new_entry_from_issue.mjs`
- Front-matter validation in CI — `scripts/check_front_matter.rb`

Change a field, run `npm run generate` (or use `/setup/`, which regenerates it for you), and the submission form, issue template and validator all update together.

## Top-level structure

```yaml
entry:
  singular: "Use case"   # how one entry is referred to in the UI
  plural: "Use cases"
  path: "catalog"          # folder + URL base for entries — keep as "catalog" unless you know why
  sort: "published"         # default catalog ordering key
  sort_order: "desc"        # asc | desc

sections:
  details: "Details"    # sidebar heading labels on the entry detail page
  links: "Links & resources"
  contact: "Contact"

fields:
  - key: …
    …
```

`entry.path` is also read by `_plugins/modules.rb` (to know which pages belong to the `catalog` module) and by every script that scaffolds or reads entries (`new_entry_from_issue.mjs`, `thumbnail_sources.mjs`, `check_front_matter.rb`).

## Reserved keys

`title`, `slug`, `summary`, `published`, `thumbnail`, and `featured` are always present on every entry, whether or not you list them under `fields`. `title` and `summary` should still be declared as fields (they are, in the shipped schema) so they render in the submission form; `slug`, `published`, `thumbnail`, and `featured` are set automatically when an entry is scaffolded and are maintainer/automation-managed, not submitter-facing.

## Field spec

Each item under `fields` is a hash with these properties:

| Property | Meaning |
|---|---|
| `key` | Front-matter key. `snake_case`, unique, required. |
| `label` | Human label shown in the form, issue template, and detail page. Required, must be unique. |
| `type` | One of `text`, `textarea`, `markdown`, `url`, `email`, `select`, `multiselect`, `list`, `date`, `number`, `boolean`, `file`, `image`. See below. |
| `required` | `true`/`false` (default `false`). Enforced in the web form, the issue form, and `check_front_matter.rb`. |
| `description` | Help text shown under the field in forms. |
| `placeholder` | Example text shown in forms. |
| `options` | List of allowed values — `select` and `multiselect` only. |
| `facet` | `true` → appears in the filter panel (`_includes/facet-filters.html`) and gets a `data-facet-<key>` attribute on cards for client-side filtering. `select` → single-choice filter; other types → multi-choice. |
| `card` | `true` → shown on catalog cards. `select` → badge over the thumbnail; `list`/`multiselect` → chips (max 4 shown, overflow collapses to a `+N` chip); `text` → meta line under the title. |
| `search` | `true` → included in `/search.json` (the Lunr index). `title` and `summary` are always indexed regardless. |
| `section` | `details` \| `links` \| `contact` — which sidebar group the field renders in on the entry detail page. Defaults by type when omitted: `url`/`file` → `links`; `email` or a key containing `contact` → `contact`; everything else → `details`. |
| `form` | `false` → hidden from both submission forms (the web form and the issue form). Use for maintainer-only fields, e.g. `featured`. |
| `thumbnail` | `file` fields only. `true` → CI renders `thumb.jpg` from this PDF's first page (`thumbnails.yml` workflow, `scripts/thumbnail_sources.mjs`). |
| `filename` | `file` fields only. The expected filename inside the entry folder, e.g. `deck.pdf`. |

### Field types

| Type | Storage | Notes |
|---|---|---|
| `text` | string | Single line. |
| `textarea` | string | Multi-line, plain text. |
| `markdown` | — | Becomes the page **body** (the Markdown after front matter), not a front-matter key. Only one field may be `markdown`. |
| `url` | string | Must start with `http://` or `https://` (enforced by `check_front_matter.rb`). Rendered as a link with a host label. |
| `email` | string | Must contain `@`. Rendered as a `mailto:` link. |
| `select` | string | Single choice from `options`. |
| `multiselect` | YAML list | Multiple choices from `options`. |
| `list` | YAML list | Free-form: one item per line in the issue form, comma-separated in the web form. |
| `date` | `YYYY-MM-DD` | Rendered with `date: '%B %-d, %Y'`. |
| `number` | number | No unit or range validation beyond presence. |
| `boolean` | `true`/`false` | Rendered as Yes/No. |
| `file` | string (path) | An attachment the maintainer adds to the entry folder in the pull request after scaffolding; front matter stores `/​<entry.path>/<slug>/<filename>`. Set `thumbnail: true` on a PDF field to auto-generate a card thumbnail. |
| `image` | string (path or URL) | When the key is `thumbnail`, used as the entry's card/detail image (see `_includes/entry-thumb.html`'s fallback order: explicit `thumbnail` → auto-generated `thumb.jpg` → branded initials placeholder). |

## Example entry front matter

```yaml
---
title: "Multilingual Environmental Complaint Intake"
slug: 311-multilingual-intake
summary: "Cloud-hosted service that translates and classifies resident complaints…"
published: 2026-05-02
featured: true
organization: "Los Angeles County Department of Public Health"
solution_type: "Cloud deployment (AWS, Azure, GCP)"
domain:
  - "Environmental health"
  - "Communications & outreach"
ai_tools:
  - "Amazon Bedrock"
  - "AWS Lambda"
  - "Amazon Translate"
stage: "In production"
repo_url: ""
demo_url: ""
docs_url: "https://example.org/eh-intake-architecture"
vendor: ""
data_sources:
  - "311 API"
  - "Web complaint form"

---
## Overview
…the markdown field's content becomes the page body…
```

See `catalog/311-multilingual-intake/index.md` and the other four sample entries in `catalog/` for full working examples.

## Changing the schema

1. Edit `_data/schema.yml` — add, rename, remove, or reorder fields. Reordering changes form/sidebar order.
2. Run `npm run generate` (or use `/setup/`, which does this for you) to rebuild `.github/ISSUE_TEMPLATE/new-entry.yml`.
3. Run `npm run validate` to confirm the schema itself and existing entries are still consistent.
4. **Renaming or removing a field does not update existing entries.** Their front matter keeps the old key until someone edits the Markdown files (or you script a migration); `check_front_matter.rb` will flag entries that are now missing a newly-required field.
5. Commit both the schema change and the regenerated issue template together.

## Cohort/program data (module: `cohorts`)

Each `_data/cohorts/<year>.yml` file describes one cohort page (`cohorts/<year>/index.md`, `layout: cohort`):

```yaml
title: "AI Practice Cohort 2026"
events:
  - id: kickoff
    name: "Cohort kickoff"
    date: 2026-09-09
    time: "12:00–1:30 PM ET"
    location: "Zoom"
    type: "Session"
    description: "…"
materials:
  program_guides:            # group key -> label is the key, title-cased ("Program guides")
    - title: "Cohort handbook"
      type: "guide"
      url: "https://…"
  templates:
    - title: "Evaluation plan template"
      type: "template"
      url: "https://…"
policies:
  - "Teams work only with data they are already authorised to use."
  - "Each team publishes one catalog entry by the final showcase."
```

- `materials` is a **hash** of group key → list of `{title, url, type}`; the group key is rendered as the section heading with underscores turned into spaces and title-cased (`_includes/materials.html`).
- `policies` is a flat list of plain strings, rendered as a bulleted list.
- `events` entries here are merged with `_data/events.yml` by `_plugins/events.rb` into `site.data.events_all` (see below).
- Entries belong to a cohort by setting a `cohort` field in their front matter (e.g. `cohort: "2026"`) matching the year — this is not a schema field by default in the shipped AI-catalog config; add one (`select`/`text`, `facet: true`) if you want entries to be assignable to cohorts through the schema.
- Cohort event detail pages live at `cohorts/<year>/events/<event-id>/index.md` (`layout: event`) and pull their date/time/location/materials from the matching entry in the cohort's `events` list unless the page's own front matter overrides them.

## Events data (module: `events`)

`_data/events.yml` is a flat list of site-wide events:

```yaml
- id: ai-community-call-sept
  name: "AI in Public Health Community Call"
  date: 2026-09-16
  time: "1:00–2:00 PM ET"
  location: "Zoom"
  url: "https://example.org/community-call"
  type: "Webinar"
  description: "…"
```

`end_date` is optional (for multi-day events). `_plugins/events.rb` normalizes and merges this list with every cohort's `events` into `site.data.events_all`, sorted by date, with a computed `past` boolean and (for cohort events with a matching page) a `page_url`.

## Resource library data (module: `resources`)

`_data/resources.yml` is a list of groups:

```yaml
- group: "Getting started"
  description: "…"          # optional
  items:
    - title: "Responsible AI use checklist"
      url: "https://…"
      type: "Guide"           # optional; shown as a chip
      description: "…"        # optional
```
